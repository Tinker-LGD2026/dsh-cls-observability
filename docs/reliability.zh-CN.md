# 可靠性：退出、崩溃、Pod 丢失时数据怎么保住

[English](reliability.md)

本文说明插件把还没送达的 Span 存在哪里、各种故障下这些数据会怎样，以及插件对你运行 DSH 的环境有哪些要求，供你做部署评审时参考。DSH 本身怎么部署由你决定，插件去适配它。

## 一句话版本

- 每个 Span 先写进本地的写前日志，**再**发送；CLS 确认收到后才删除。
- 正常退出时，没发完的数据写进待发箱目录，由一个短时运行的后台进程发完。
- 崩溃、`kill -9`、内存不足被杀、Pod 被删之后留在磁盘上的数据，由**下一个**使用同一目录启动的插件进程补发，换一台机器挂载也可以。
- 所以前提是：这个目录还在，并且之后会有进程在它上面再次启动；如果你的运行环境会和 DSH 一起结束，就要在结束前运行一次 `--flush`。

## 数据存在哪里

插件只使用一个目录：`$DSH_HOME/agentobs/outbox`，或 `CLS_AGENTOBS_DATA_DIR` 指定的绝对路径。DSH 只提供 `$DSH_HOME` 这个位置，目录里的内容全部由插件写入和删除。里面存的是已经转换好的 Span，不是 DSH 的会话（DSH 自己的会话记录在 `$DSH_HOME/sessions` 下）。

| 文件 | 是什么 | 何时删除 |
|---|---|---|
| `<时间>-<进程号>-<随机>.wal` | 写前日志分段（每段不超过 4 MiB）：产生一个 Span 写一行，送达后追加确认行 | 段内全部 Span 都已确认，或已转成待发文件 |
| `<时间>-<进程号>-<随机>.otlp.gz` | 一个可直接发送的请求（gzip 压缩的 OTLP/protobuf，最多 512 个 Span、约 4 MiB） | CLS 已接收，或因内容问题拒收（HTTP 400 / 413） |
| `… .sending-<进程号>.<命名空间>` | 上面两种文件被某个进程“认领”后的名字 | 认领释放或文件删除 |
| `open-spans`、`open-spans-<进程号>.<命名空间>` | 进行中的轮次已经发出了哪些 Span | 启动时合并；保持在 4 MiB 以内 |
| `closed-turns` | 崩溃后已经补全过的轮次 | 保持在 4 MiB 以内 |
| `*.corrupt` | 读不出来的日志，单独放在一边 | 不自动删除（检查后手动删除） |

目录权限 `0700`，文件 `0600`。目录如果是符号链接或属于其他用户，插件拒绝使用。待发箱上限 512 MiB，超出后新的转存会被拒绝并记录日志。

## 一个 Span 的经历

```
产生 ──► 写前日志 (.wal) ──► 内存队列 ──► 批量发送 ──► CLS 确认 ──► 删除
                                 │
              正常退出时          ├──► 待发文件 (.otlp.gz) ──► 后台补发进程 ──► 删除
              内存队列放不下时    └──► 待发文件 (.otlp.gz) ──► 由运行中的宿主发送
```

- **写前日志**：Span 产生时同步写入；每 200 毫秒请操作系统落盘一次（在后台线程执行，不占宿主主线程）。
- **内存队列**：每 2 秒或每 512 个 Span 发一批。遇到网络错误、超时、HTTP 408 / 429 / 5xx 时重试，间隔从 1 秒逐步拉长到 60 秒；遇到 401 / 403 / 404（密钥或主题问题）时暂停 5 分钟，数据全部保留。
- **正常退出**：DSH 给插件约 5 秒。插件立刻把没发完的数据写成待发文件，拉起一个后台补发进程，同时自己继续发送，直到截止时间（默认 3.5 秒）。

## 留下来的文件由谁发

任何使用这个目录的插件进程都会处理遗留文件，包括 DSH 宿主、后台补发进程、`--flush`、`--relay`：发现待发文件就发送，发现已经不在的进程留下的写前日志，就先转成待发文件。动一个文件之前，先把它改名、加上自己的标识（`<进程号>.<命名空间>`），算作“认领”，所以两个进程不会发同一个文件。

怎么判断文件的主人已经不在了：

| 主人 | 规则 |
|---|---|
| 同一个 PID 命名空间（同一台机器或同一个容器） | 它的进程号已经不存在 |
| 不同的 PID 命名空间（另一个 Pod、sidecar） | 它的文件 **2 分钟**没有刷新。活着的进程每 30 秒刷新一次 |

运行中的宿主在启动时检查一次，之后每分钟检查一次。所以旧 Pod 死掉后，它留下的数据大约 2–3 分钟内会被替换它的新 Pod 接手。

## 各种故障下的结果

| 发生了什么 | 没送达的数据在哪 | 由谁补发 |
|---|---|---|
| 正常退出（任务完成、Ctrl-C、SIGTERM） | 待发文件 | 后台补发进程立即发送；没发完的下次启动时发 |
| `kill -9`、内存不足被杀、宿主崩溃 | 写前日志 | 下一个在该目录上启动的插件进程 |
| CLS 一段时间不可达 | 内存；队列满了（2 万个 Span 或 256 MiB）转成待发文件 | CLS 恢复后由运行中的宿主发送 |
| 密钥或主题配错 | 保留，暂停发送 | 改好后由运行中的宿主发送（改环境变量需要重启） |
| 机器断电 | 写前日志，最后约 200 毫秒还没落盘的部分可能丢失 | 下一个插件进程 |
| 进程管理器停止服务，并结束其中所有进程（systemd 默认如此） | 待发文件；后台补发进程也被结束 | 停止后运行 `--flush`（例如 `ExecStopPost=`）；否则下次启动时发送 |
| 容器退出（主进程结束） | 待发文件；后台补发进程随容器一起被杀 | 由 `examples/container/entrypoint.sh` 这类包装脚本在容器停止前运行 `--flush`；没发完的由卷上的下一个容器发送 |
| 短时环境结束（CI 任务、Serverless、沙箱） | 待发文件，不 flush 就会随环境一起丢弃 | 环境的最后一步运行 `--flush` |
| Pod 被删除（`kubectl delete pod`） | 同正常退出，在宽限期内完成 | 入口脚本的 flush；没发完的由卷上的下一个 Pod 发送 |
| Pod 被杀、被驱逐，或节点丢失 | 卷上的写前日志或已认领的待发文件 | 下一个挂载该卷的 Pod，在哪个节点上都可以 |
| 目录没了（`emptyDir`、节点磁盘被清空） | **丢失** | — |
| 之后再也没有进程在这个目录上启动 | 留在磁盘上，不会发送 | 手动运行 `node dsh-cls-observability.mjs --flush <目录>` |

被崩溃打断的那一轮，缺少的入口、Agent、步骤、工具 Span 也会补上，但要等 DSH 续跑这个会话（DSH 在续跑时才写入关闭这一轮的事件）。崩溃后再也没续跑的会话，这一轮会一直缺这几个 Span。

## 重复

Span 的 ID 是根据会话内容算出来的，补发时 ID 不变。已经确认送达的 Span 不会再发；崩溃补全时会跳过死掉的进程已经发出去的部分。唯一会重复的情况：CLS 已经收下一批请求，但回复还没送到，进程就死了，这一批会再发一次。

## 插件对运行环境的要求

不管怎么部署，只有两个条件：

1. **数据目录比 DSH 进程活得久**（`$DSH_HOME/agentobs/outbox`，或 `CLS_AGENTOBS_DATA_DIR`），而且之后还会有进程在它上面启动：DSH 本身、`--flush` 或 `--relay` 都可以。
2. **如果运行环境会和 DSH 一起结束，结束前先把剩下的数据发出去**（`--flush`）。

对应到常见的部署方式：

| DSH 运行在哪里 | 数据目录 | DSH 停止后由谁发送 |
|---|---|---|
| 工作站、虚拟机 | 本地磁盘 | 后台补发进程；否则下次启动 |
| 进程管理器（systemd 等）托管的服务 | 本地磁盘 | 停止后运行 `--flush`（例如 `ExecStopPost=`），或下次启动 |
| 你的程序通过 TypeScript SDK 拉起 | 该次拉起的 `DSH_HOME` | 后台补发进程（你的程序还在运行） |
| 容器 | 挂载的卷，而不是容器自己的文件系统 | 包装脚本在 DSH 之后运行 `--flush`；否则由卷上的下一个容器发送 |
| Kubernetes | 替换的 Pod 会重新挂载的 PVC；一块盘同一时间只给一个 Pod（CBS 这类 ReadWriteOnce 云硬盘）：单副本加 `strategy: Recreate`，或 StatefulSet 的 `volumeClaimTemplates`；不要用 `emptyDir` | 包装脚本或 `--relay` sidecar；宽限期覆盖 DSH 退出加 flush 的时间（60 秒足够）；Pod 丢失后由下一个 Pod 接管 |
| 短时环境（CI、Serverless、沙箱） | 随环境一起丢弃 | 最后一步运行 `--flush`；被强制结束时没送达的数据会丢失 |

`--relay`（sidecar 或独立进程）和运行中的宿主同时存在是安全的，跨 PID 命名空间也会遵守认领。`examples/` 下的文件演示了其中一种做法，请按你的实际情况调整。

## 怎么验证的

- 单元测试与故障注入测试：写前日志、待发文件认领、跨命名空间的租约、恢复死进程的日志、崩溃补全（与 DSH 自身的关闭逻辑在 6000 多个崩溃点上逐一对照）。
- 真实 DSH，Linux 与 macOS：任务中途杀掉进程再续跑，数据全部送达，没有重复。
- TKE（Kubernetes 1.36，CBS 云硬盘，2 个 x86_64 节点），使用 `examples/kubernetes` 下的清单。每次运行都把会话记录回放出“应该产生哪些 Span”，和 CLS 实际收到的逐个比对：

| 场景 | 结果 |
|---|---|
| Job，走 CLS 内网域名，入口脚本收尾补发 | 完全一致 |
| 任务进行中 `kubectl delete pod` | 完全一致；Pod 1–2 秒内退出 |
| 任务进行中杀掉 Pod 内全部进程（`kill -9`），在另一个节点起新 Pod | 完全一致；新 Pod 启动后 1 分钟内接管了写前日志 |
| Deployment 的 Pod 在任务进行中被强制删除 | 完全一致；Deployment 重建的新 Pod 挂上同一块盘，补发了旧 Pod 留下的数据 |
| `dsh web` 加 relay sidecar | 完全一致；sidecar 没有抢宿主正在用的文件 |

集群上的这些场景都写在 `scripts/tke-verify.ts` 里。上面进程管理器（systemd）与短时环境两行基于同样的机制推导，尚未端到端实测。
